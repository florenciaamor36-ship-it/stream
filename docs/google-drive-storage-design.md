# Google Drive per-user storage design (proposal)

Status: design only. This document does not enable Drive storage, change the deployed app, migrate records, or access any database/user record.

## Audit snapshot

The current web app does not use Firebase Authentication, Firestore, or Google OAuth for user sign-in/storage. It has a custom email/password login and registration flow in `src/lib/storage.ts`/`src/components/AuthModal.tsx`, server API routes in `server.ts`, and a `localStorage` fallback for static hosting. The server path is file-backed; static-host fallback keeps data in that browser's local storage. The existing UI/API functions assume that same server-or-local-storage persistence model; Drive is not a drop-in backend today. `package.json` has no Google OAuth/Drive client dependency and `.env.example` has no OAuth client-ID setting. No database file or live user records were inspected.

## Supported design

1. **Keep app authentication separate from Drive authorization.** Preserve the existing app login only as the app's identity/session mechanism; require a separate, user-initiated Google OAuth consent before accessing Drive. Never reuse the assistant's connected Google account or an operator credential. With only the minimum `https://www.googleapis.com/auth/drive.appdata` scope, the app can read/write its own hidden `appDataFolder`; that scope does not identify the Google account. If the product needs to show/bind a verified Google address, request Google identity (`openid email`) separately and explain that additional permission; otherwise show a clear account-selection/connection step without pretending the app-login email proves Drive ownership.
2. **One private data file per Drive identity.** Store a versioned JSON envelope in that consenting user's `appDataFolder` (e.g. schema version, app data payload, update timestamp, client/write ID). Search for the app's known filename in `appDataFolder`; create on first use, update thereafter. Never store OAuth client secrets in the browser. Keep access tokens in memory only; request new consent/token after expiry/reload rather than persisting tokens in local storage. Let the user disconnect/revoke access.
3. **Integrate at the storage boundary, not per screen.** Introduce a storage provider interface used by *all* reads and mutations (including backup/restore, settings, services, sales, accounts, customers, templates, and tokens). Add Drive as an explicit opt-in provider; do not silently switch the current server backend to Drive. Scope data by the active app user and reject records belonging to another app user. A Drive-mode session must not call server data endpoints or write to the server's shared JSON store. Preserve current local/offline mode as an explicit fallback.
4. **Offline and conflict behavior.** Maintain a local snapshot/outbox for offline edits and show which provider is active and last successful sync. On reconnect, fetch the latest file metadata/revision and compare with the revision last read before uploading. If it changed, do not silently overwrite: keep the local pending copy, offer reload/export/replace or a record-aware merge, and make the user choose. Serialize writes in one tab and use Drive file update as a whole-file replacement (atomic at the individual file operation level), retaining revision metadata; Drive is not a transactional database and cannot safely provide concurrent multi-device record-level writes without this conflict handling. Never claim background multi-user collaboration.
5. **Backups and schema.** Keep the existing user-initiated JSON export/import, add Drive-specific export/restore guidance, and include schema version/migration tests. A backup downloaded by a user remains under their control; do not create a service-account/shared-drive copy. Test empty folder, first create, repeat read/update, token expiry, denied consent, offline edits, stale revision conflict, import/export, and isolation between two separately authorized Google accounts.

## Google Cloud and deployment setup required

A browser-only OAuth app needs a real Google Cloud **OAuth 2.0 Web client ID** (public identifier, not a client secret), the Google Drive API enabled in the project, an OAuth consent screen configured for the app/audience, and authorized origins matching the deployed site plus any local development origin. During external-app testing, add the intended test users; complete any Google verification/review Google requires before broad public use. Put only the client ID in deployment configuration (for example `VITE_GOOGLE_CLIENT_ID`) and document it as public config; do not commit a fabricated ID, client secret, refresh token, API private key, or user token. No billing enablement is required for this design.

At audit time the repo contains no OAuth client ID/origin configuration, no Drive integration, and no established user-level storage-provider contract. There is no configured credential available for this app's Google Cloud project and no user-supplied client ID/origin or confirmation of the target deployment origins. Therefore the code cannot make a real Drive OAuth request or be end-to-end tested yet. The owner must create/configure the OAuth client in their own Google Cloud project and provide the public client ID plus exact deployment origins (never a secret); then implementation/testing can proceed. This design leaves existing production data/auth untouched.

## Product boundary

Google Drive here is personal storage for the Google account that explicitly authorized this app. It is not automatically a shared database between app variants/devices: both must implement the same versioned record schema and authorize the same Google account (or explicitly support an intentional shared identity) before records are interoperable. Drive appData content is private to the authorizing app/account and is not a substitute for a transactional multi-user database.
